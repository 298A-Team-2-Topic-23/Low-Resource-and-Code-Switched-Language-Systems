# Synthetic code-mixing

Linear **298-17** (pipeline, fixture batch) and **298-76** (first run on a real corpus).
Generated by scripts; do not edit the JSON files by hand.

## Status, stated precisely

**The pipeline has run on a real, contamination-checked corpus. Its output is not yet fit to
train on.** What exists:

- IBM Model 1 alignment by EM, no external aligner and no network
- Equivalence-Constraint block segmentation over the alignment (monotonic blocks, not a parser,
  so this is **not GCM output** and must not be reported as such)
- selection matched to a target switch-point fraction rather than uniform
- a measured Romanisation step in front of the generator (`lrcs.data.transliterate`)
- a contamination gate on the generated output (`--gate-manifest`)
- automatic defect counts on the output (`scripts/codemix_quality.py`)

No model has been trained on any of it. Model 4 is 298B work; this is its input stage.

## Step 1: Romanisation, and how wrong it is

Samanantar's Hindi is Devanagari. The generator refuses Devanagari on purpose, and that refusal
is unchanged. Romanisation is a separate step in front of it: the Dakshina lexicon first (most
attested spelling, ties broken alphabetically), then rules with schwa deletion for words the
lexicon lacks. Anything left in Devanagari is still refused by the generator.

Measured against 100 held-out Dakshina sentences that a person Romanised by hand (seed 42):

| Metric | Value |
|---|---|
| Character error rate | **8.6%** |
| Word exact match, 1,483 words | **71.3%** |
| Lexicon path / rule path | 70.1% / 72.6% |
| Rule fallback alone, 100 unseen words, matches any attested spelling | 49.0% (CER 17.9%) |

"Exact match" is scored against **one** annotator's spelling, so `nahi` against `nahin` counts
as wrong although both are correct. Much of the 28.7% miss rate is that variance rather than
error, and that variance is what this project studies. The rule fallback is the weak path. On the
slice, 222,781 of 267,818 Devanagari words (83.2%) came from the lexicon and 45,037 by rule. No
row is still above the generator's 5% Devanagari limit.

## Step 2: Generation

| | Real run (298-76) | Fixture (298-17) |
|---|---|---|
| Pairs in | 29,996 | 30 |
| Sentences out | **28,559** | 13 |
| Skipped `too_few_blocks` | 1,437 (4.8%) | 17 (57%) |
| Mean alignment coverage | 0.96 | 0.93 |
| Candidate pool | 930,470, 3.1% consumed | 34, 38% consumed |
| Mean per-sentence SPF | **0.2398** (target 0.2398) | 0.2365 |
| Contamination gate on output | **passed**: 0 dev/test matches; 11 exact + 1 near train matches, kept | not run |

The fixture predicted that `too_few_blocks` would fall sharply on a real corpus. It did, from
57% to 4.8%. Model 1 needed more data to learn crossing links, and with 30k pairs it has them.

**Two SPF definitions; do not compare across them.** The target 0.2398 is HinGE's
**corpus-level** SPF (total switch points over total token boundaries). The generator matches its
**mean per-sentence** SPF to that number. Measured the same way on both sides, the batch is
0.238 corpus-level against HinGE's 0.2398, and HinGE's own mean per-sentence SPF is 0.272. So the
batch switches slightly less per sentence than HinGE. If the target is meant to be per-sentence,
it should be 0.272. That needs a team decision before M4 data is regenerated.

## Step 3: Quality, and why this batch is not training data

Meeting the switch target says nothing about whether the sentences read as language.
`codemix_quality.py` counts two defects a human would see at once:

| Defect | Rows | Share |
|---|---|---|
| A word occurs more often than both sources allow (`new new`) | 8,127 | **28.5%** |
| A pair of English words appears in reverse source order | 15,630 | **54.7%** |
| Neither defect | 10,307 | 36.1% |

The fixture batch, by comparison, has 0% repeats and 15.4% inversions.

The 36.1% is an **upper bound** on usable rows, not an estimate of it. The repeat check misses
words that occur in both the English and the Hindi (`NIA`, `is`), and neither check sees dropped
content. A few rows from the batch (Samanantar, CC-BY-NC-4.0; quoted for evaluation):

| English source | Generated |
|---|---|
| The various measures taken by Railways inter alia include | bachat ke liye Railways ke vibhinn upaayon mein shamil hain |
| This is the power of democracy | democracy of the power hai |
| Weve fulfilled the aspirations of the people | Weve aspirations of the people aspirations ko fulfilled aspirations |
| You may have incorrectly typed the location | aapane shayad galat sthan incorrectly |

The first reads as plausible Hinglish. The others show the failure modes:

1. **English realised in Hindi word order.** Blocks follow the Hindi side, so English words
   inside a block can come out reversed.
2. **Repeated words.** Model 1 links many Hindi words to one English word, and each link can
   realise it again.
3. **Loose source pairs.** Samanantar is partly web-mined. "I am going to be in Delhi for Diwali"
   is paired with Hindi meaning "I live in Delhi". No aligner can fix a pair that is not a
   translation.

These belong in the failure analysis, not behind a filter. Before M4 trains on this, the team
should decide on a filter (drop rows with either defect, or a fluency score) and a human check of
a sample. Neither is done here.

## Licence: why the real batch is not committed

The batch derives from Samanantar (treated as CC-BY-NC-4.0, team decision in
`docs/datasheet.md`) and from the Dakshina lexicon (CC BY-SA 4.0, share-alike). Share-alike
requires derived data to carry CC BY-SA. The non-commercial term forbids uses that CC BY-SA
permits, so no single licence covers the combination for redistribution. The batch stays in
gitignored `data/interim/`. Only counts, hashes and the four quoted rows above are committed.
Anyone who needs the batch regenerates it with the commands above.
