# 3.3 Data Pre-processing

Linear **298-63**. Written by Thomas Lnu, Shibin Biji.

Pre-processing is stage 2 of the pipeline (`src/lrcs/data/clean.py`). It decides which records
are usable as supervision, removes the rest with a stated reason, and tags every surviving
token with its language. Every count here comes from the real HinGE run of 8 October
(`reports/data_statistics.json`, run record `runs/20261008T043208Z_data-pipeline_seed42.json`,
input SHA-256 `dcfaf37c…`). None was typed in by hand.

## 3.3.1 What pre-processing removes, and how many

Stage 1 hands stage 2 **4,799** records, one per human reference. Six filters run in a fixed
order, and **each record is charged to the first filter that rejects it**, so the counts sum to
the total rather than overstating it.

| # | Filter | In | Removed | Out | % | What it rejects |
|---|---|---|---|---|---|---|
| 1 | `missing_field` | 4,799 | 0 | 4,799 | 0.00% | English or Hinglish empty after normalisation |
| 2 | `not_romanized` | 4,799 | **25** | 4,774 | 0.52% | Reference more than 20% Devanagari |
| 3 | `untranslated` | 4,774 | 0 | 4,774 | 0.00% | Reference identical to the source |
| 4 | `length_bounds` | 4,774 | **87** | 4,687 | 1.82% | Under 2 or over 60 words on either side |
| 5 | `length_ratio` | 4,687 | **11** | 4,676 | 0.23% | Hinglish:English word ratio outside 1/3–3.0 |
| 6 | `exact_duplicate` | 4,676 | **2** | 4,674 | 0.04% | Same pair as an earlier record |
| | **Total** | **4,799** | **125** | **4,674** | **2.60%** | |

Attrition is small because HinGE is curated and human-written. The two zeros are still
informative and are checked rather than assumed: no reference is empty, and no annotator copied
the English through untranslated. The attrition table keeps three record ids per filter, so a
removal can be traced to a record without redistributing corpus text.

## 3.3.2 Why each threshold is set where it is

Pipeline defaults (`DEFAULTS` in `clean.py`), recorded in every run under `params.clean`, each
chosen for a reason about the task rather than tuned to the corpus.

| Parameter | Value | Why |
|---|---|---|
| `max_devanagari` | 0.2 | The target is **Romanized** Hinglish, so a mostly-Devanagari reference would train the wrong script. 0.2 rather than 0 tolerates a stray danda or one glossed word — the kept reference with the most Devanagari glosses `jeevan ke aam star(स्तर)` and is good. Both removed samples score 1.00. M1's smoke run emitted Devanagari in 13 of 48 outputs, so references must not teach the same error |
| `min_words` | 2 | A one-word reference has no switch point, so CMI and SPF are undefined and the pair teaches lookup, not generation |
| `max_words` | 60 | Keeps source, prompt and target inside the 512-token training context at the measured Hinglish fertility. Truncating instead would train on an incomplete sentence. Cost: 87 records; kept data still spans 3–60 English words, 95th percentile 37 |
| `max_ratio` | 3.0 | Mean Hinglish:English ratio is **1.062** — code-switching is near length-neutral, so a 3× difference indicates misalignment, not style. Applied in both directions; removed 11 |

`exact_duplicate` uses the same `dedup_key` as the split stage (NFKC, lower-case, punctuation to
space). Near-duplicates are deliberately **not** removed here; they are grouped at the split
stage so every member of a cluster lands in one split, because deleting them would discard
legitimate alternative references.

## 3.3.3 Language tagging

Every token is tagged in the LinCE scheme (Aguilar et al., 2020): `lang1` English, `lang2`
Romanized Hindi, plus `ambiguous`, `ne`, `other`, `unk`. The tagger is a documented, ordered
rule list, not a learned model, and its Hindi markers include every surface form in
`analysis/spelling_variants.tsv`, so a variant such as `nhi` is tagged rather than left unknown.

On the real corpus it resolves **68.2%** of tokens. §3.6's code-mixing statistics are computed
over resolved tokens only, and that coverage figure is quoted with them every time. Tagging
adds the `tags` field, which is why pre-processed records carry 7 fields against a raw
record's 6.

removing good short references. `23d8e2aa…` is the glossed-Devanagari case the 0.2 tolerance
exists for.

## 3.3.5 Validation

Validated by tests and a gate, not by inspection. `tests/test_pipeline.py` asserts that each
filter removes exactly its own defect and that ingested minus removed equals kept
(`test_each_filter_removes_its_own_defect`), that the tagging rules resolve as documented, that
the four stages run as one command, and that **the leakage gate fails the run rather than
warning** (`test_pipeline_halts_on_injected_leak_and_writes_no_manifest`). Sample selection is
deterministic at a fixed seed. On the real corpus the gate found **0 exact and 0 near-duplicate
overlaps** across all three split pairs.

# 3.4 Data Transformation

Linear **298-63**. Written by Thomas Lnu, Shibin Biji.

Five changes of form between the released file and the TSV the model scripts read. Each has a
stated reason and none changes what a reference says.

**One rule governs all of them: spelling is never normalised in the corpus.** The orthographic
variance of Romanized Hinglish (`nahi`, `nhi`, `nahin`) is the phenomenon this project measures;
normalising it would delete the spelling-variant burden §3.6 reports and leave the Model 3
hypothesis with nothing to act on. Normalisation exists in exactly one place, inside the
normalised-chrF++ metric, which says so in a comment: *"used for the normalised metric ONLY.
Never normalise training data or the gold references themselves."*

## 3.4.1 The transformations

| # | Transformation | Where | Why |
|---|---|---|---|
| 0 | Fetch at a pinned revision | `fetch_data.py` | Retrieved at `e25a1038`, hash-verified, licence and citation recorded. A source with no licence is refused |
| 1 | Pickle to CSV *(no longer required)* | `convert_hinge_pkl.py` | Retained for anyone holding the pickle release — see below |
| 2 | Column selection | Stage 1 | Only English, Hindi and the human Hinglish references carry forward; the machine-generated WAC/PAC outputs and ratings are not supervision for this task |
| 3 | Unicode NFC + whitespace collapse | Stage 1, `normalise()` | One code-point sequence per grapheme, so two strings differ only when their text differs. Applied once, so later stages cannot disagree |
| 4 | One record per reference | Stage 1 | HinGE stores several references per source in one list cell; supervision needs one pair per row |
| 5 | Split TSV layout | Stage 3 | The five columns the model scripts read |

> **Correction, 10 November 2026.** This section was written believing HinGE is released only
> as a pandas pickle with no stated licence. That is wrong: the authors' lab publishes
> `HinGE.csv` at `LingoIITGN/HinGE` under **CC-BY-4.0**, and the published CSV hashes to
> `dcfaf37c…` — the identical value recorded for the pickle conversion's output. Same bytes,
> pipeline unaffected. The safeguards below are kept because they remain correct for anyone
> holding the pickle, and ingest still refuses `.pkl`. Owner: Waghmare, 298-75.

Unpickling untrusted data can execute arbitrary code, so ingest refuses `.pkl`
(`test_ingest_refuses_pickles`) and the converter is the one controlled place it is opened.
Three safeguards: the file is refused before opening unless its SHA-256 matches
(`--expected-sha256`); a restricted unpickler allows only pandas and numpy classes plus
`functools.partial` and `builtins.slice`, so `os.system` raises before it is called; and
`tests/test_convert_hinge_pkl.py` builds a pickle whose payload calls `os.system` and asserts
it is refused with no output written.

## 3.4.2 Normalisation, before and after

`normalise()` applies NFC and collapses whitespace runs, including non-breaking spaces. It runs
inside ingest, so no un-normalised record survives to show; these are its real outputs:

| Input | Output | What changed |
|---|---|---|
| `"kya  tum⍽aaj   shaam free ho? "` (⍽ = non-breaking space) | `"kya tum aaj shaam free ho?"` | Double, non-breaking, triple and trailing spaces each collapse |
| `cafe` + combining acute (5 code points) | `café` (4 code points) | Decomposed becomes precomposed; the two now compare equal |

Case, punctuation and spelling are untouched: `Main`/`main` and `nahi`/`nhi` stay distinct.

## 3.4.3 One source row to several records

1,976 rows become **4,799** records, a mean of **2.41** references per source. The spread is
uneven:

| References per source | 1 | 2 | 3 | 4 | 5 | 6 | 7 | 8 |
|---|---|---|---|---|---|---|---|---|
| Sources | 26 | 1,470 | 166 | 210 | 37 | 21 | 5 | 3 |

**Four of the eight references** for source row 3 (*"In the year 1985-86, the erstwhile Ministry
of Welfare was bifurcated into the Department of Women and Child Development and the Department
of Welfare."*):

| ref | hinglish |
|---|---|
| 0 | In the year 1985-86, purvarti kalyan mantralay was bifurcated into mahila aevam baal vikaas vibhaag and kalyan vibhaag. |
| 1 | Varsh 1985-86 mein erstwhile Ministry of Welfare ko department of women and child development aur department of welfare mein vibhaajit kiya gya tha. |
| 5 | In the year 1985-86, poorvavarti kalyan mantralay ko mahila aivam baal vikas vibhag and kalyan vibhag me bifurcate kiya. |
| 7 | poorvavarti kalyan mantralay ko year 1985-86 me mahila aivam baal vikas vibhag aur kalyan vibhag me bifurcate kiya gaya tha. |

**This is the clearest argument for not normalising spelling.** One sentence, written by humans,
yields `purvarti`/`poorvavarti`, `vikaas`/`vikas`, `vibhaag`/`vibhag`, `aevam`/`aivam`,
`gya`/`gaya`. The references also disagree about which words stay English (`bifurcated`) and
which become Hindi (`vibhaajit`). Normalising the first erases what §3.6 measures; the second
is the code-switching itself.

The list cell is parsed with `ast.literal_eval`, which accepts literals only and never evaluates
code. Each record keeps `row` and `ref` so it traces back to the release. Two consequences the
later sections depend on: **splits are made by source, not by record**, so all references of one
sentence share a split — otherwise a model could be tested on a sentence whose other references
it trained on; and **evaluation scores each source once against all its references** (§4.4),
because the test split holds 468 records but only 197 sources, so per-record scoring would
weight a source by how many references it happens to have.

## 3.4.4 Identifiers and the split layout

Both identifiers are derived from content, so they mean the same thing on every machine. The
**record id** is the first 16 hex digits of SHA-256 over the `dedup_key` of English and
Hinglish, so a whitespace-only difference cannot mint a new id. The **group id** is the
lexicographically smallest `dedup_key` in a near-duplicate cluster; before this it depended on
set iteration order, which made the split non-deterministic until it was fixed in Cycle 2.

Stage 3 writes `data/processed/hinge/{train,dev,test}.tsv` — gitignored, with their SHA-256
digests committed in the split manifest. Five columns: `id` (cites a record without
redistributing its text), `group` (keeps clusters in one split and allows grouping at
evaluation), `english` (model input), `hindi` (needed by the baseline's two-input condition),
`hinglish` (training target and reference). The stage-2 `tags` field is not written, which is
why records go from 7 fields to 5 between pre-processing and transformation.

**Two records from the real split files:**

| id | english | hinglish |
|---|---|---|
| `083e9734…` | The label used for menu items and buttons that activate this action. | The label used for menu items and buttons jo kriya ko activate karta hai. |
| `28e435d5…` | Is Taj Mahal in realty the Temple of Lord Shiva? | Is taj mahal in reality shiv ka mandir. |

`group` is the `dedup_key` of the English source; `english` and `hinglish` keep their original
case and punctuation, because only the grouping key is normalised.
