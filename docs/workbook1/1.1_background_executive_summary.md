# 1.1 Project Background and Executive Summary

Author: Savalia, Jenil Sanjaybhai · Issue 298-32

Natural language processing quality falls off sharply outside the highest-resource languages, and it falls off again for code-switched text, the mixed-language writing that bilingual communities actually produce. Hindi–English code-switching, usually called Hinglish, is the everyday written register of a very large bilingual population on messaging apps, social media and customer-support channels. A sentence such as "Main market ja raha hoon, jaldi aa jao yaar" carries Hindi grammar in Roman script, with English words placed wherever they fit. Conversational assistants, moderation pipelines, search interfaces and support automation deployed across South Asia receive this kind of input every day, yet they are built and benchmarked mostly on monolingual data, so their real failure rate on their own traffic is rarely measured. The need is therefore twofold: a system that generates natural Hinglish, and an evaluation method that exposes how much quality is lost when the target is code-switched rather than monolingual. The problem matters beyond one language pair, because Spanglish, Taglish, Arabizi and many other pairs written in an adopted script sit in the same position.

The target problem is a single generation task: given an English sentence, produce its Romanized Hinglish equivalent. Quality loss on low-resource and code-switched text is usually blamed on missing data, and, for languages written in a non-Latin script, on tokenizer inefficiency; recent work shows that romanizing Indic text substantially reduces the number of tokens a model spends per word (Husain et al., 2024). Hinglish, however, is already written in Roman script, so if its token fertility is still high, neither explanation covers it. Our hypothesis is that the dominant hidden cost is orthographic variance: nahi, nhi, nahii and nahin are one word, but the tokenizer sees them as four unrelated vocabulary entries, and the model must learn each one separately from very little data. The goal of the project is to determine, under controlled conditions, which adaptation strategy most improves English-to-Hinglish generation per unit of compute, to attribute that improvement to a specific cause, and to validate it with native speakers rather than with automatic metrics alone.

The scope is deliberately narrow so that the comparison can be controlled. In scope are one language pair (Hindi–English), one generation task (English to Romanized Hinglish), four models built on one shared backbone, and one reproduced published baseline. Out of scope are a learned language-identification model for Romanized Hinglish, which is a research problem in its own right and is why token-level language tags in this project will be assigned by a documented rule-based marker list rather than a trained tagger; speech and audio code-switching; other language pairs; pretraining a model from scratch; and production deployment beyond a single-GPU serving demonstration. Naming these exclusions keeps the work achievable for five students over two semesters and makes clear which questions the results can and cannot answer.

The approach is an ablation ladder of four models, each adding exactly one ingredient so that each step isolates one competing explanation. Model 1 is the instruction-tuned backbone prompted zero-shot; it adds nothing and measures how large the problem is. Model 2 adds task supervision through parameter-efficient fine-tuning (QLoRA) on real code-switched pairs, and tests whether the gap is simply missing task data. Model 3 adds representation, extending the tokenizer vocabulary with Hinglish subwords followed by continued pretraining, and tests whether the gap is the tokenizer. Model 4 adds distribution, training on synthetic code-switched and back-translated text, and tests whether the gap is the scarcity of code-switched data. Two control arms keep the attribution honest: continued pretraining without vocabulary extension, so that a Model 3 gain can be credited to the new vocabulary rather than to extra training, and Model 2 trained to the same GPU-hours as Model 3, so that "Model 3 wins" cannot simply mean "Model 3 received more compute". All arms share one backbone, whose exact model identifier will be fixed only after it is verified against the official model card, and every configuration runs under three random seeds (13, 42 and 1337) with GPU-hours logged per run. Separately from the four models, we reproduce the mBART system of Gahoi et al. (2022) for the WMT 2022 MixMT Subtask-1, whose published Table 2 reports ROUGE-L 0.617 and WER 0.633, to within 0.01 ROUGE-L; the reproduction exists to prove that the evaluation harness is correct, and no model result is interpreted until it lands within tolerance.

Parallel supervision comes from the HinGE corpus (Srivastava and Singh, 2021), which contains 1,976 English–Hindi sentence pairs with human-written Hinglish references. The paper reports 4,803 human references; counting directly off the released file gives 4,799, and that four-item discrepancy is recorded as open rather than silently resolved. The team is also building an 800-item, three-column evaluation set of English source, Devanagari Hindi reference and Romanized Hinglish reference; its schema, annotation guidelines and validator are in the repository, and its items are still to be authored. The third column is what makes the code-switching penalty measurable: the same English source is scored against a monolingual Hindi reference and against a Hinglish reference, and the difference is the cost of code-switching. chrF++ is the primary metric, because character n-grams tolerate Romanized spelling variation in a way BLEU does not; normalised chrF++, BLEU, ROUGE-L and WER are secondary, and a new spelling-variant burden metric, the mean number of tokens a tokenizer spends per surface form across known spellings of one word, tests the orthographic-variance hypothesis directly. Blinded native-speaker raters judge adequacy, fluency and code-switching naturalness, with Krippendorff's alpha reported for each dimension. Success is defined in advance as at least 3 chrF++ points over the zero-shot baseline with non-overlapping error bars across the three seeds; a difference under 1 chrF++ point, or one with overlapping error bars, is reported as a null result. A null result is an acceptable outcome and is pre-committed to, because a tightly controlled ablation that rules out an explanation is itself a finding.

The project is expected to contribute, to our knowledge, the first measurement of orthographic-variant burden on Romanized code-switched Hindi, reported alongside tokenizer fertility and vocabulary coverage and correlated with output quality; a controlled attribution of quality gains between vocabulary extension and continued pretraining, which prior work has not separated; a released three-column benchmark with annotation guidelines and a datasheet that exposes the code-switching penalty directly; a code-switching naturalness dimension for human evaluation that standard machine-translation protocols lack; and a public repository with pinned dependencies, recorded seeds and per-run compute logs that an outside team can rerun. The immediate applications are language technologies serving South Asian users, including conversational assistants, customer-support automation, content moderation and search query understanding, which can use the benchmark to measure their failure rate on real code-switched traffic for the first time. Because the pipeline is parameterised by language rather than hard-coded, the same adaptation protocol, fixed-compute design and orthographic-variance analysis carry over to other code-switched pairs written in an adopted script, which lowers the barrier for language communities where no such work yet exists.
