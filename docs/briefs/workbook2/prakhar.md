## 298-67 — section 4.2

This is the weakest row in Progress Report 2's Part A: Complete 55%, Document 40%, and the only
Planning figure below 100% on the whole table at 90%. So there is real ground to make up.

Two halves, and the marks are in the second:

> (1) describe the platform, environment and tools supporting development and execution of **each** model
> (2) provide **sufficient and excellent diagrams** of platform architecture, components, ML data flows

### Part 1 — platform and environment, per model

What exists and can be cited:

- `requirements.txt` with pinned versions, including `transformers==4.57.6` and the reason the
  pin exists — the unpinned requirement resolved to 5.x in Colab and broke `TrainingArguments`
- `common/repro.py` — `set_seed` and `RunLogger`; seven run records under `runs/`
- `docs/COMPUTE_BUDGET.md` — 0.112 GPU-hours spent against 80–145, per-arm reservations, and the
  bf16-on-Turing tripwire
- `docs/COMPUTE_ALLOCATION.md` and the fallback runbook from your PR #33
- the Colab T4 path: 4-bit NF4 quantisation, device-aware precision selection, persistent
  checkpoint directory, resumable notebook
- local Apple Silicon machines for CPU-side development and tests — which is *why* the 4-bit
  branch could not be tested locally and had to be proven on a T4

Say per model what each needs. M1 inference only. M2 a single quantised GPU. M3 more memory for
the extended embedding matrix. M4 a reverse model plus GCM. **Be honest that no allocation is
confirmed** — 298-51 and 298-10 are open — and give the fallback. A resource section that
implies compute we do not have is the kind of thing Part D already contradicts.

### Part 2 — the diagrams, which do not exist

The README has architecture sketches, but nothing satisfying "platform architecture, components,
machine learning data flows". Produce three, **each generated by a committed script** so a reader
can regenerate them:

1. **Platform architecture** — dev machines, Colab/cloud runtime, storage, where artifacts land,
   what is version-controlled against what is not
2. **ML data flow** — raw source → four pipeline stages → frozen splits → training → adapters →
   generation → evaluation harness → `results/` and `runs/`
3. **Component diagram** — modules in `src/lrcs/`, `models/`, `evaluation/`, `analysis/` and
   what depends on what

Commit under `reports/figures/` with the generating script. Hand-drawn images nobody can
regenerate are the one thing this project has avoided everywhere else, and the same rule is why
the Gantt and PERT charts are scripted.
